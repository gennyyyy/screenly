# Plan

Fix the confirmed missing-cursor path before attempting further visual tuning. The Android client currently ignores `CursorPos`, the Windows engine no longer sends that message, and both capture backends rely solely on unchecked `DrawIconEx` calls; therefore any native cursor lookup, bounds check, or draw failure produces no cursor at all. The last saved GDI capture sample contains no cursor, but without the cursor’s position and API results it cannot distinguish an out-of-display pointer from a failed native draw; the precise failing Win32 condition still needs runtime evidence.

## Scope
- In: Restore the known visible marker path, identify the exact native capture failure, correct native cursor rendering, preserve a fallback for both codecs, and verify the exact Windows/Android builds in use.
- Out: Touch injection, cursor theme editing, new cursor-image transport, and latency work. Do not remove the fallback unless native cursor presence is verified frame by frame.

## Action items
[ ] First restore the last known visible behavior: reinstate Windows `CursorPos` broadcasts and Android position/visibility state, then render the yellow marker in a shared overlay above both JPEG and H.264 video. Verify the marker on the Android device before investigating native drawing further.
[ ] Record the actual running Windows executable version/path, Android app version, negotiated codec, selected monitor device name, capture dimensions/origin, and virtual-display position. Do not assume the source tree’s current codec matches the deployed configuration.
[ ] Add one temporary, sampled native-cursor diagnostic in each capture backend (`GdiCapture.TryGetFrame` and `DxgiCapture.TryGetFrame`) that reports: `GetCursorInfo` return value; flags and handle validity; screen and monitor-local coordinates; whether the coordinates pass the capture-bounds test; `DrawIconEx` return value and last error; and whether a known visible cursor is present in the output frame. Capture a frame with the pointer centered over a high-contrast test area before it is streamed.
[ ] Fix the exact failed predicate revealed by that capture: use the same selected monitor’s physical origin and dimensions as the captured frame, ensure cursor coordinates are in that coordinate space, and do not silently skip an in-bounds visible cursor. Correct `DrawIconEx` placement using the cursor hotspot from `GetIconInfo`; its `xLeft/yTop` parameters specify the image’s upper-left corner. Free the bitmaps returned by `GetIconInfo`.
[ ] Composite the native cursor before encoding in both active capture backends and propagate a `cursorAuthoritative` bit in an unused video-frame flag. Set it only when cursor state was read successfully and a visible cursor was successfully drawn (or a successfully queried hidden state was confirmed). Check drawing results instead of treating an attempted call as success.
[ ] Keep Android’s yellow marker as a permanent safe fallback: hide it only when the corresponding frame has `cursorAuthoritative=true`; otherwise show it at the latest valid `CursorPos`. Keep this shared across JPEG and H.264 so failure in either capture path cannot become a blank cursor.
[ ] Validate each branch independently: native draw success hides the marker and matches the host cursor; hidden Windows cursor hides both; `GetCursorInfo` failure, out-of-bounds coordinates, or `DrawIconEx` failure keeps the marker visible. Test arrow, I-beam, hand, resize, custom, monochrome, high-contrast/large cursors, hotspots, four edges, capture restarts, and both codecs.
[ ] Install matching Windows and Android builds, record their versions and codec, compare the captured pre-stream frame with the Android output, and confirm the 30 FPS minimum remains stable. Remove temporary diagnostics only after the failure predicate and successful fallback/native cases are documented.

## Open questions
- None blocking. The plan assumes the yellow marker is an acceptable permanent fallback whenever native cursor state is not confirmed in a frame.
