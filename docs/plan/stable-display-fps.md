# Plan

Raise the Android second display to a sustained, measured 30 FPS minimum, with a 60 FPS mode when the PC, phone, and link can sustain it. The current working path captures with GDI, JPEG-encodes synchronously, waits 33 ms after processing (so work time is added to the frame interval), then Android decodes JPEG and draws it on the UI event collector; the H.264 encoder is only a stub. Measure every stage first, then move the normal path to asynchronous display capture and hardware video encode/decode, with a measured fallback and explicit frame-rate negotiation.

## Scope
- In: Windows capture, encoding and pacing; frame transport and backpressure; Android receiving, decoding and presentation; FPS configuration, reporting, instrumentation, and sustained throughput validation.
- Out: Reducing end-to-end latency as a separate goal, cursor/touch features, audio, security, and unrelated UI or architecture work. Queues must remain bounded to protect throughput, but latency tuning is deferred.

## Action items
[ ] Establish a trustworthy baseline in `Screenly.Engine/Program.cs`, `GdiCapture.cs`, `Session.cs`, `MainActivity.kt`, `ScreenlyClient.kt`, and `VideoDecoder.kt`: count captured, encoded, sent, received, decoded, dropped, and presented frames; record per-stage processing times and frame intervals using a monotonic clock; expose rolling 1-second and 10-second FPS plus drop counts. Update `docs/plan/performance-audit.md` so stale estimates are labeled and replaced with measurements from the current build.
[ ] Add an explicit target FPS to `EncodingConfig` and negotiation (30 FPS default; optional 60 FPS), clamp it to the virtual display refresh rate and supported encoder/decoder rates, and report the actual selected rate in `HELLO_ACK`/`CONFIG` rather than advertising the display refresh rate as stream FPS.
[ ] Replace the additive `TryGetFrame`/`Task.Delay(33)` loop with a monotonic deadline-based producer and independent capture/encode/send stages. Keep queues bounded, track each drop/backpressure reason, and ensure a slow client cannot stall capture or other sessions; do not mistake a 30 ms processing time plus a 33 ms delay for a 30 FPS cadence.
[ ] Implement the planned Windows DXGI Desktop Duplication capture for the selected virtual display, including stable texture reuse, frame timestamps, display-change recovery, and clean resource ownership. Retain GDI/JPEG as a fallback only when benchmarked settings can sustain the selected target; make fallback and any reduced resolution/quality visible rather than silently claiming 30 FPS.
[ ] Complete `H264Encoder` using Windows Media Foundation with hardware encoder selection where available, low-latency settings only as needed for throughput, no B-frames, timestamped output, and keyframe/configuration handling. Add a software encoder fallback and a documented JPEG fallback; negotiate codec, dimensions, bitrate, and FPS with Android and select a mode only after capability checks.
[ ] Decouple Android socket reads from rendering in `ScreenlyClient` and `MainActivity`: use a bounded frame handoff, perform JPEG decode away from the UI collector if fallback remains, and use MediaCodec callbacks or a dedicated decode/render worker for H.264. Handle codec input-buffer exhaustion, output draining, surface recreation, and format changes while counting frames actually presented (not merely received or queued).
[ ] Add automated checks for target-FPS negotiation and unsupported-rate fallback, deadline pacing under variable work time, queue bounds/drop accounting, capture/encoder failure recovery, frame timestamps, protocol codec/format changes, and Android decoder frame accounting. Add a Windows benchmark for 720p and 1080p at 30 and 60 FPS to compare capture, encode, and send capacity independently.
[ ] Verify on representative Windows PCs and Android devices over the intended USB path and Wi-Fi if supported: run dynamic full-screen content for at least 10 minutes at 1080p30, then 720p60 and 1080p60 where hardware permits; record rolling presented FPS, frame drops, stage timings, CPU/GPU use, temperature/thermal throttling, and link throughput. Acceptance: at least 30 presented FPS on average and in at least 95% of rolling 10-second windows for the 30 FPS profile, without sustained thermal or queue growth; higher modes must be labeled by their measured capability. Recheck reconnects, resolution changes, and encoder/decoder fallback.
[ ] Package matching Windows and Android releases, document supported FPS/resolution combinations and fallback behavior, and provide a rollback to the known working JPEG path if a device-specific hardware codec fails.

## Open questions

- Is the intended deployment USB-only, or must 30 FPS also hold over Wi-Fi? Treat USB as the required path until clarified.
